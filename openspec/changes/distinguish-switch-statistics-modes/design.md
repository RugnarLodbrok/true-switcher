# Design

## Context

`input` уже различает `AutoSwitchKind::Regex` и `AutoSwitchKind::Dictionary` при выборе цели, но при создании `SwitchRequest` сводит оба варианта к `SwitchMode::Auto`. `switcher` использует этот режим и для выбора настройки звука, и для статистики.

## Goals / Non-Goals

**Goals:** сохранить источник выбранного правила до записи статистики, не меняя поведение коррекции и звука.

**Non-Goals:** восстанавливать тип старых записей или менять приоритет правил.

## Decisions

Передавать тип выбранного автоматического правила через запрос коррекции до записи `switches`. Это позволяет записать фактическую причину свича, включая случай, когда подходят оба правила. Альтернатива — повторно определять причину при записи — может расходиться с исходным выбором и зависит от изменившегося состояния.

Оба автоматических типа продолжают использовать `auto_switch_sound`; ручной — `manual_switch_sound`. Существующие строки базы не мигрируются: по их содержимому нельзя надёжно определить тип автоматического свича.

## Risks / Trade-offs

- [Старые и новые записи `mode=1` имеют разную семантику] → документировать ограничение в README; дата события сама по себе не определяет версию приложения.
- [Откат приложения снова создаёт неоднозначные `mode=1`] → учитывать это при анализе данных; откат не переписывает уже созданные строки `mode=2`.
