# Задача 24.17. Уточнить время жизни данных запроса исправления

ЗАДАЧА ОТКЛОНЕНА

Место: `src/input.rs`, `Input`; `src/switcher.rs`, `Switcher::process_requests` и `Correction::from_input`.

## Вывод после обсуждения и сверки с кодом

Первоначальное предложение — объединить этапы захвата в машину состояний через `enum` — не обосновано. Последовательность ожидания запроса, входа в захват, исправления и выхода уже выражена потоком исполнения в `Switcher::process_requests`. Внутри `Input::enter` последовательно выполняются ожидание клавиш, попытка захвата и при необходимости восстановление с повтором. Отдельный `enum` этапов потребовал бы синхронизации с этим порядком вызовов.

Задача не требует отдельной машины состояний, нового компонента или переноса управления в `Input::process_message`. Количество флагов само по себе не доказывает необходимость рефакторинга.

## Что действительно хранится между вызовами

- `pending` содержит источник ожидающего запроса. После успешного `enter` он очищается, но `is_auto_request` и `automatic_target` ещё используются в `Correction::from_input`. Это данные с разным временем жизни, а не просто поля одного ожидающего запроса.
- `automatic_target` может исчезнуть при сохранении автоматического запроса: например, после Backspace или Space. Тогда `Correction::from_input` возвращает `None`, и захват завершается без исправления. Обязательная цель в варианте `Automatic` без изменения обработки событий не сохранит это поведение.
- `is_original_switch_key_held` отличает исходное нажатие клавиши переключения при ожидании остальных клавиш. `is_switch_key_reset` внутри `enter` отдельно сохраняет факт её сброса между повторными попытками.
- `recording` доступен обработчикам событий во время входа в захват. При раннем выходе с ошибкой `Drop` использует его для сбора данных восстановления. Это не просто локальная переменная, которую можно убрать из `Input` без замены механизма очистки.
- `is_captured` задаёт поведение общих обработчиков событий и очистки. Фактический захват отдельных устройств хранится в `Source::is_grabbed`: при частичном захвате `is_captured` ещё равен `false`.
- `repair` и `repair_prepared` сохраняют незавершённое восстановление после ошибок. `rollback` удаляет выполненные действия, а `Drop` повторяет оставшиеся. `repair_prepared` пополняется до записи нажатия, поэтому его нельзя трактовать как перечень гарантированно успешных записей.
- `is_cancel_requested` — потребляемое уведомление для потока исправления. `is_correction_cancelled` сохраняет факт отмены после потребления уведомления, чтобы поздний успешный `CorrectionFinished` не обновил историю. Эти флаги не дублируют друг друга. `correction_result` хранит результат до его получения вызывающим кодом.
- `is_backing_off` и `HoldDetector` описывают независимое ограничение ввода, которое действует и вне захвата. Их не требуется включать в общий `enum` этапов.

## Возможное полезное изменение

Сузить рефакторинг до представления запроса и передачи его данных из `Input::enter` в создание `Correction`. Цель — явно различить ожидающий запрос и данные принятого запроса, которые нужны после захвата, вместо сохранения последних в отдельных полях `Input` после очистки `pending`.

Конкретный API ещё не выбран. Кандидат для обсуждения: успешный `enter` возвращает данные принятого запроса, а `Correction::from_input` получает их явно. При этом до успешного завершения `enter` обработчики событий должны сохранять возможность обновить или обесценить автоматическую цель. Отдельно проверить, можно ли объединить источник, вид запроса и сведения об исходном нажатии без усложнения повторных попыток.

Это локальное улучшение читаемости и времени жизни данных, а не исправление установленной ошибки. Если после определения API выигрыш окажется меньше сложности передачи контекста, задачу можно закрыть без изменения кода. Объединение остальных полей в структуры само по себе не является критерием выполнения.

## Границы и проверка при реализации

Сохранить текущий порядок обработки очереди и таймеров удержания. Не переписывать управление захватом, back off и восстановлением ради унификации типов.

Использовать существующие тесты `src/input.rs` как основу проверки поведения:

- ручные и автоматические запросы, исчезновение автоматической цели после последующих событий;
- отмена при ожидании клавиш и во время входа, повтор входа после восстановления;
- частичный захват устройств и повтор неудавшегося отпускания клавиши при очистке;
- отмена исправления после потребления уведомления и поздний успешный результат;
- отложенные изменения раскладки и согласование истории при выходе из захвата.

Согласовать представление запроса с дальнейшими изменениями результата исправления. Самостоятельная общая машина состояний больше не является ожидаемым результатом задачи.
